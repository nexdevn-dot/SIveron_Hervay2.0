# Platform shell, controls, settings and help

Code checked: 2026-10-23. [Index](../INDEX.md) · [Development](../DEVELOPMENT.md)

## Purpose and workflow

The sidebar selects workspace sections; the header provides agent start/stop,
appearance, language and refresh. Agent status is separate from discovery and
sending pause. Today summarizes counts, decision requests and activity. Usage
reports expose model/service utilization; unavailable usage is not zero usage.
Settings expose configured integrations and sending controls. Native delivery readiness now uses read-only heartbeat observations
(PID/time/model/reply safety and relevant configuration hash); unknown/stale evidence
is not reported as ready. See [delivery](delivery.md). Secret values must
never enter documentation or screenshots used as test fixtures.

The technical package/CLI/logger namespace remains `harvey`; visible branding is
Siveron. Renaming technical paths is a migration, not a global text replacement.
The local runtime pins Codex and enforces tool isolation, auth/version checks and
capability-tested model support. Global Codex configuration is outside this project.

## Next-action queue (R05, implemented 2026-10-19)

`work_items.py` derives operational tasks from current records rather than storing
notifications. GET `/api/work-items?page=1` returns 30/page with an uncapped total;
GET `/{key}` rechecks the task before navigation and returns 410 if resolved/changed.
Today shows the queue alongside existing setup/research prompts, removing its old
generic approval/reply notifications. Exact pending/approved message stats are uncapped.

- Reply tasks require a meaningful final incoming message in an open/replied thread.
  Outgoing-only, answered, closed and corrupt/empty threads do not generate tasks.
  Review acknowledgment stores a digest of incoming receipts/content, not a changed
  conversation/contact lifecycle. A fresh incoming reply invalidates acknowledgment.
- Pending-review messages group once per campaign. Approval/rejection/cancellation
  resolves the task on the next read. Opening it does not approve anything.
- Approved messages use the same delivery readiness/context/runtime assessment as the
  Outbox. Blocked/unknown messages group once per campaign with reasons and next steps.
  Ordinary schedule, predecessor/delay, quiet-hour and cap waits alone are not tasks.
  Sending/cancellation or resolved blockers remove the task; it is not dismissible by
  pretending the transport succeeded. No model/provider connection preflight is run.

Tasks navigate to the exact conversation or an exact-message scoped Outbox view,
including older records beyond standard list limits. Single-message views hide bulk
approval. The existing explicit per-message approval, suppression and sending gates
remain. Conversation detail is fetched again for display and review fingerprint so
review never acknowledges newer content than the thread being shown.

Implementation: `campaign_results.py` owns reply receipts/review endpoints;
`operations.js` owns DE/EN navigation and pagination. Tests: `test_work_items.py`;
`test_campaign_results.py` covers explicit outcomes. No new chart dependency.

## Quota freshness (2026-10-20)

Usage shows the UTC fetch-completion timestamp formatted locally, independently of
provider reset times. Quota clients retain their five-minute success cache and
one-minute failure backoff. Explicit Refresh quota now calls `/api/usage?refresh=true`
and bypasses the cache under the existing client lock. It reads limits only, without
a model prompt, token generation, auth renewal or agent start. A failed read clears
the displayed quota instead of retaining a stale number. Dashboard event totals
remain Siveron-only; the subscription gauge represents the selected provider bucket.

## In-app assistant (2026-10-20)

`assistant.py` installs GET/POST `/api/settings/assistant`, POST `/api/assistant/chat`
and read-only POST `/api/assistant/report`. Typed Pydantic plans follow the TypeChat
schema/validation pattern; TypeChat itself is not installed. The existing restricted
Brain produces JSON without host tools. Invalid/extra fields fail closed; unsupported
criteria yield clarification. No model-generated SQL is executed. There are no
assistant send, approval, deletion, signal-activation or research-start endpoints.

Deep Chat 2.5.1 is locally bundled by `tools/assistant-chat`, used by `web/assistant.js`
and `assistant.css`. A nonmodal side panel preserves the current workspace and has
DE/EN labels, examples, busy/error/empty states, clear and Escape/close controls.
Search proposals populate existing Discover fields after an explicit click; the
existing preview/run/provider/signal gates remain. Data results open existing company
profile dialogs. Pagination repeats validated queries without another model call.

Preferences persist as `settings.assistant_settings`: enable/name, interface-matched
or DE/EN response language, brief/detailed style, feature scopes (help/navigation,
discovery, inventory analysis), 0–6 previous turns, 1–30 visible rows, and bounded
answer guidance. They cannot replace Brain/provider/model configuration or approval
rules. Each chat request rereads preferences. Chat history is memory-only, cleared
on reload or Clear; prior text is transmitted only within the configured bound.
Already displayed messages are not retroactively translated. Saved companies and
report rows are computed locally and not supplied to the model; explicit user text,
bounded prior dialogue, signal definitions and help excerpts are supplied.

Help retrieval uses at most three bounded bilingual excerpts from generated
`web/assistant-help.json`, authored in `help-content.js` and regenerated by the manual
export script. Query interpretation includes schema, enabled capabilities and signal
catalog. No whole database, credentials or private configuration is included.

Inventory uses parameterized name/location/industry substring queries, active company
rows only. Signal reports reuse `target_profiles.evaluate_profile`: current active
signal, evidence age/confidence and latest fact rules retain match/no_match/unknown.
Counts cover the filtered inventory; visible rows paginate. Summary counts are per
signal within a category, overlap across signals, and are not unique category totals.
Unsupported numeric employee/revenue predicates, campaign comparisons, combined
signal expressions and contact-email filters require clarification rather than a
relaxed query. Source evidence and query time accompany results; they do not prove
external completeness. Tests: `tests/test_assistant.py`; browser tests use isolated
SQLite and mocked Brain, not live AI access or sending.

## Assistant preference switches (2026-10-22)

The four boolean assistant preferences use the same green/gray switch track and
white thumb as Signals. Native checkbox inputs expose role=switch and retain
checked/form serialization, label activation and Space-key support. Focus is
visible and motion respects reduced-motion preferences. Changes still require
Save assistant settings; this visual update does not enable any preference or

changes are preserved by the existing form renderer.

## UTF-8 model context on Windows (2026-10-23)

Assistant help JSON and Brain prompt/skill Markdown are read explicitly as UTF-8,
independently of the host locale. CP1252 regression tests preserve German and
non-Latin text without decode errors or mojibake. No model access or capability
checks change. CI prints individual test names, stops on the first failure and
bounds each matrix job to 20 minutes for actionable cross-platform diagnostics.
